# Extending ffight-disasm to Alien vs. Predator

Both goals are viable. The native port already exists in beta, and the byte-identical disassembly has no public implementation but needs only one new technical piece on top of the Final Fight toolchain. **tmcleroy/cps2recomp** (GPL-3.0-only) ships a statically recompiled native build of AvP for Linux x86_64/ARM64, macOS, Windows and Android on SDL 3. Its AvP port is at "Beta", with **82,889 68000 instructions found, 25 left to an interpreter guess, and the Z80 QSound driver translated (2,153 instructions)** as of 2026-10-18 ([PROGRESS.md](https://github.com/tmcleroy/cps2recomp/blob/HEAD/games/avsp/PROGRESS.md)). It publishes names and addresses only and no reassemblable listing, so a byte-identical AvP disassembly would be new work. No IDA/Ghidra database, annotated `.asm` or matching decompilation of AvP was found. The one CPS1-to-CPS2 problem without an off-the-shelf tool is opcode encryption. Rebuilding the four original program chips requires decoding instructions from a decrypted view and **re-encrypting exactly the opcode-fetched words** with an inverse of MAME's Feistel cipher, which MAME does not provide. Of the user's tooling, the decoder, discovery, coverage checker, trace collector and verification design transfer directly, while the ROM combiner, SHA-1 table, hardware symbols and bot need per-game edits. The recommended path builds the disassembly as a private generated source with public tools (the ffight-disasm model), uses cps2recomp as a differential reference instead of writing a second runtime, and starts a native port only for something cps2recomp lacks (readable C, widescreen, three-player netplay, no distributed binaries).

## cps2recomp already runs AvP natively; no public disassembly exists

cps2recomp describes itself as "unofficial native PC ports of Capcom CPS-2 arcade games ... via static recompilation", in which "each game's 68000 program is translated ahead of time into C++ ... The board (video, the QSound chip, the sound CPU, the settings memory) is code written for this project, not an emulator" ([README](https://github.com/tmcleroy/cps2recomp/blob/HEAD/README.md)). The repo was created 2026-10-13, holds **724 commits (706 by the author)**, lists 29 CPS-1/CPS-2 games, and was pushed 2026-11-09 ([repo](https://github.com/tmcleroy/cps2recomp)). AvP targets `avspu` (USA 940520) and accepts `avsp`, `avspj`, `avspa` and `avsph` as the same program revision. It rejects sets without the key file or with pre-2021 dumps of `avp.14m/16m/18m/20m` ([games/avsp/README.md](https://github.com/tmcleroy/cps2recomp/blob/HEAD/games/avsp/README.md)). The project's own status reads "nobody has played it by hand yet". Endings are unreached, two music cues are unplaced, sound "has not been listened to", and weapon heat and Predator cannon variables are unfound ([PROGRESS.md](https://github.com/tmcleroy/cps2recomp/blob/HEAD/games/avsp/PROGRESS.md)). Features include three players, start at any of 7 rounds, score attack, stage and model viewers, cheats, custom soundtrack and run-ahead. Widescreen is explicitly not enabled for AvP ([NATIVE_VIDEO.md](https://github.com/tmcleroy/cps2recomp/blob/main/docs/NATIVE_VIDEO.md)).

Two other AvP repositories exist. **omegakatana92/Alien-vs-Predator-arcade-Recomp-** (2026-10-17) vendors cps2recomp v0.3.0, accepts only `avsp`, and states "`games/avsp/src/` is empty" ([PROGRESS.md](https://github.com/omegakatana92/Alien-vs-Predator-arcade-Recomp-/blob/HEAD/games/avsp/PROGRESS.md)). **princeendo/avp_saturn_version** (2026-11-06) has size 0 ([repo](https://github.com/princeendo/avp_saturn_version)). GitHub and GitLab searches for avsp disassemblies returned nothing else, and zengfr's shared IDA databases list other Capcom beat-'em-ups but not AvP ([zengfr README](https://github.com/zengfr/ida-pro-idb-database/blob/main/README.md)). sudden-desu.net has a disassembly-based article on AvP debug tools and alternate staff credits, readable only via search summary in the research session ([sudden-desu](https://sudden-desu.net/entry/alien-vs-predator/)).

Community RAM knowledge is cross-validated across independent sources. The mame-rr hitbox script (2011) gives players at **0xFF8380 (3 × 0x100)** and enemies at **0xFF9280 (0x18 × 0xC0)**, plus projectile and misc tables ([beatemup-hitboxes.lua](https://github.com/TASEmulators/mame-rr/blob/HEAD/mame-rr/lua/beatemup-hitboxes.lua)). FBNeo cheats place P1 health at FF83C1, lives at FF8471, character at FF8452 and region at FF81C9 ([avsp.ini](https://github.com/finalburnneo/FBNeo-cheats/blob/master/cheats/avsp.ini)). cps2recomp's `avsp.h` and PROGRESS.md give the richest map, with A5 = FF8000, the attract routine table at 004706, round table at 00CCA0, camera driver 0AF858, enemy allocator 01769E, object draw 0A9B48, settings copy routine 003C5E, and the Z80 song table at 9006 ([avsp.h](https://github.com/tmcleroy/cps2recomp/blob/HEAD/games/avsp/src/avsp.h)). These sets agree on the player base, stride, health, lives, character and clock offsets (inference from comparison of the three sources). HBMAME carries six AvP hacks from 2017 to 2020, three on `dead_cps2` with decrypted program ROMs ([cps2mis.cpp](https://github.com/Robbbert/hbmame/blob/master/src/hbmame/drivers/cps2mis.cpp)). No TAS was found.

The only official re-release is the 2019 Capcom Home Arcade, emulated with FB Alpha. AvP was absent from the 2018 Beat 'Em Up Bundle and both Capcom Arcade Stadium collections, which press coverage attributes to licensing without a primary source ([Nintendo Life](https://www.nintendolife.com/news/2022/06/oops-it-looks-like-capcom-arcade-2nd-stadiums-line-up-has-leaked); [HG101](https://www.hardcoregaming101.net/alien-vs-predator-capcom/)). The game was never ported to a home console. The Jaguar and SNES "Alien vs Predator" titles are different games, and MAME's Jaguar software list reuses the short name `avsp` ([jaguar.xml](https://github.com/mamedev/mame/blob/master/hash/jaguar.xml)).

## Opcode encryption is the only new obstacle to a byte-identical rebuild

AvP is a standard CPS-2 board with no game-specific protection in MAME. The program is **2 MiB in four 512 KiB `ROM_LOAD16_WORD_SWAP` chips**, and only the first two chips differ between regions ([MAME cps2.cpp](https://github.com/mamedev/mame/blob/master/src/mame/capcom/cps2.cpp)).

| Item | Value (MAME `avsp`) |
|---|---|
| CPUs | 68000 @ 16 MHz (MAME clock scale 0.7375), Z80 @ 8 MHz, 250 Hz Z80 IRQ |
| Program chips | `avpe.03d` @0x000000, `avpe.04d` @0x080000, `avp.05d` @0x100000, `avp.06` @0x180000 |
| Region-specific | 03d/04d only; 05d and 06 shared |
| Key | 20 bytes per region (`avsp.key` CRC e69fa35b) |
| Graphics | 12 MiB, 8 chips, `ROM_LOAD64_WORD` + per-2 MiB-bank unshuffle |
| Sound | Z80 `avp.01` 128 KiB (unencrypted), QSound samples 4 MiB |
| Video | 384×224, 8 MHz / (512 × 262) = 59.637 Hz |
| Inputs | `cps2_3p3b`, 3 players × 3 buttons, 93C46 EEPROM |

The cipher "only affects opcodes, not data" and computes `D = FN2(E, K XOR EX(FN1(A, K)))` from two 4-round Feistel networks over the opcode word and the low 16 bits of its address ([cps2crypt.cpp](https://github.com/mamedev/mame/blob/master/src/mame/capcom/cps2crypt.cpp)). The key unpacks into a 64-bit master key, watchdog instruction words, and an upper limit `upper = (((~decoded[9] & 0x3ff) << 14) | 0x3fff) + 1` with lower limit 0 ([cps2.cpp](https://github.com/mamedev/mame/blob/master/src/mame/capcom/cps2.cpp)). MAME maps the decrypted image as a separate `AS_OPCODES` space, and its 68000 core routes each access to the opcode or program space by the microcode's SSW_PROGRAM/SSW_DATA classification ([m68000gen.py](https://github.com/mamedev/mame/blob/master/src/devices/cpu/m68000/m68000gen.py)). `cps2crypt.cpp` contains no encrypt function. MAME's cipher, video and both QSound implementations are **BSD-3-Clause**, while FBNeo's copy of the cipher carries a non-commercial licence unsuitable for reuse ([FBNeo license.txt](https://github.com/finalburnneo/FBNeo/blob/master/src/license.txt)). MBDesu/cps2-utils (MIT, TypeScript) claims encryption but leaves decrypt and encrypt unchecked in its own TODO list ([cps2-utils](https://github.com/MBDesu/cps2-utils)).

Consequences for a rebuild follow from the cipher structure (inference unless cited). Each Feistel round XORs one half with a function of the other, so running the rounds in reverse with the same per-address subkeys inverts FN2, and `decrypt(encrypt(x)) == x` over all 65,536 word values per address class is a complete self-test. The generator must read instruction and extension words from the decrypted image and absolute data from the raw image, then emit a bitmap of opcode-fetched words for a post-link encrypt step. Bytes the generator does not claim as code can be emitted from the raw image, so **byte identity is always reachable and the quality metric becomes code coverage**, as it already is for Final Fight. A word mislabelled as code or data produces wrong ciphertext and fails SHA-1, which adds an independent anti-cheat check that CPS1 lacks.

One question remains open in the notes. Whether PC-relative operand reads such as the jump-table load `move.w (T,pc,d0.w),d0` go through decryption decides which image the jump-table follower reads and whether table words belong in the encrypt bitmap. cps2recomp's toolkit states "The CPS2 key ciphers PC-relative data reads" in connection with a Super Turbo jump table ([TOOLKIT.md](https://github.com/tmcleroy/cps2recomp/blob/main/docs/TOOLKIT.md)), which indicates yes for that game. Confirmation on one AvP table by diffing MAME `saveo` (opcode space) against `save` (program space) at the table address settles it for this set ([MAME memory.rst](https://github.com/mamedev/mame/blob/master/docs/source/debugger/memory.rst)).

The decrypted Phoenix set `avspd` is no shortcut to the target. It keeps `avp.05d` byte-identical to the encrypted sets but changes `avped.03d`, `avped.04d` and `avpd.06`, and MAME warns that Phoenix sets were hand-modified for the dead-board memory map and "sometimes errors introduced" ([cps2.cpp](https://github.com/mamedev/mame/blob/master/src/mame/capcom/cps2.cpp)). The identical `avp.05d` implies either that the encrypted range ends at or below 0x100000 or that the chip holds no executed code (inference). cps2recomp places animation lists at 15E240+ and pictures in 100000–1FFFFF, consistent with both readings. Decoding the key locally gives the exact limit.

## The Final Fight toolchain transfers with four structural changes

ffight-disasm is about **1,155 lines** of Python, C, Lua and shell, committed in 11 commits over roughly two hours on 2026-11-08 ([repo at 677ddd1](https://github.com/cerroverb/ffight-disasm/tree/677ddd11232d47faa14c0cfcf1f4e04f56063a25)). It generates GNU-as source with explicit operand sizes, finds code by recursive descent from vectors, MAME traces, manual entries and PC-relative word jump tables, round-trips every instruction through the assembler, and falls back to tagged raw words where GNU as re-encodes ([gen.py](https://github.com/cerroverb/ffight-disasm/blob/677ddd11232d47faa14c0cfcf1f4e04f56063a25/tools/gen.py)). Verification has four layers, namely per-chip SHA-1, a coverage check that parses the assembler listing, an objdump cross-check of raw fallbacks, and five mutation tests, with CODEOWNERS on `/verify/`, `/Makefile`, `/traces/` and `/.github/` ([check_coverage.py](https://github.com/cerroverb/ffight-disasm/blob/677ddd11232d47faa14c0cfcf1f4e04f56063a25/verify/check_coverage.py); [mutation_test.sh](https://github.com/cerroverb/ffight-disasm/blob/677ddd11232d47faa14c0cfcf1f4e04f56063a25/verify/mutation_test.sh)). Committed knowledge is small (72 names, 35 hardware symbols, 5 RAM names, one 120 s attract trace of 9,342 PCs), so the transferable value is method and tooling, not Final Fight semantics.

| Component | AvP status | Required change |
|---|---|---|
| `dis68k.py` | Transfers | Feed decrypted image; currently reads opcode and extension words from one buffer |
| `gen.py` discovery, labels, `.equ`, round-trip | Transfers in logic | Two buffers (decrypted for instructions, raw for data and `.byte`), emit opcode-word bitmap, remove hard-coded FF header and "% of 1 MiB" |
| `combine_rom.py` | Rewrite | Concatenate four word-swapped 512 KiB chips; load key; output decrypted image |
| `verify_maincpu.py` | Rewrite | 0x200000 bytes, four chips, avsp SHA-1s, preceded by re-encryption |
| `Makefile` | Edit | Add encrypt step between objcopy and verify |
| `collect_pcs.c/.py`, `check_coverage.py` | Transfer | None beyond file names |
| `mutation_test.sh`, `m5.py` | Edit | New AvP anchors; add a code/data mislabel mutation |
| `trace_bot.sh`, `bot.lua` | Edit | Driver `avsp`; coin/start on `:IN2`, P1/P2 on `:IN0`, P3 on `:IN1`; AvP player/enemy tables; three buttons |
| `hardware.txt` | Replace | CPS2 map (0x400000 object output, 0x618000 QSound RAM, 0x708000 object RAM, 0x804000–0x8040E0 I/O, CPS-A/B at 0x804100/0x804140) |
| `names.txt` | Replace | Add IRQ4 raster vector, watchdog, EEPROM routines |
| CPS-B 04 IDs, DIP ports, YM2151/OKI latches | Drop | Not present on CPS2 |

Sources for the table are the local-repo notes and the CPS2 map in [MAME cps2.cpp](https://github.com/mamedev/mame/blob/master/src/mame/capcom/cps2.cpp). Three existing limitations matter more on AvP than on Final Fight. The jump-table regexes accept only `dN.w` indices despite the commit message claiming "any index register", so `aN`/`.l` indices, `.long` pointer tables and `movea.l (T,pc,dN.w),aN; jmp (aN)` dispatch are not followed. The `--check-only` flag in the docstring is not implemented. No CI runs `make verify` ([gen.py L10, L93–L94](https://github.com/cerroverb/ffight-disasm/blob/677ddd11232d47faa14c0cfcf1f4e04f56063a25/tools/gen.py#L93-L94)). AvP shares Capcom conventions seen in Final Fight, including A5-relative work RAM at FF8000 ([avsp PROGRESS.md](https://github.com/tmcleroy/cps2recomp/blob/HEAD/games/avsp/PROGRESS.md)), but task-system and object layouts are unverified for AvP.

GNU as remains the right assembler. It is proven byte-identical on Final Fight, encryption is a separate post-link step independent of assembler choice, and vasm's VASMBSD licence restricts distribution of modified versions and commercial use ([FreshPorts vasm](https://freshports.org/devel/vasm/)). Ghidra's 68000 module and the MIT Binary Ninja m68k plugin serve as cross-check viewers only. No CPS2 loader for either exists in the sources found ([Ghidra 68000.ldefs](https://github.com/NationalSecurityAgency/ghidra/blob/master/Ghidra/Processors/68000/data/languages/68000.ldefs)).

Scale is roughly double. The program is 2 MiB against Final Fight's 1 MiB, and cps2recomp counts 82,889 instructions, about 2.9 times the 28,515 found in Konami's TMNT by cheviman's tooling (inference from two different counting methods) ([tmntarcade-decomp](https://raw.githubusercontent.com/cheviman/tmntarcade-decomp/HEAD/README.md)). Getting to a byte-exact skeleton is a matter of days on the evidence of the Final Fight commit history (inference). Naming and semantics are the long tail.

Four port strategies apply to hand-written 68000 code, and the notes rank them consistently (inference from the precedents). Static recompilation with a native board model is proven for this exact game. An interpreter shim on Musashi or Moira (both MIT) is the fastest route to a running build with exact interrupt semantics ([Musashi](https://github.com/kstenerud/Musashi); [Moira](https://github.com/dirkwhoffmann/Moira)). A manual Cannonball-style rewrite gives widescreen and higher frame rates but costs years. Matching decompilation does not apply, since no Capcom compiler is known and claims that CPS-era games were developed on Sharp X68000 machines are secondary only ([Giant Bomb](https://giantbomb.com/wiki/Platforms/Sharp_X68000)). cps2recomp documents the residual risks of recomp, namely interrupts taken only at block boundaries, which changes RNG in some games, and code reachable only under different timing, handled by an interpreter fallback and `--record-entries` ([VERIFYING.md](https://github.com/tmcleroy/cps2recomp/blob/main/docs/VERIFYING.md); [TIMING.md](https://github.com/tmcleroy/cps2recomp/blob/main/docs/TIMING.md)).

Hardware HLE needs for AvP are lighter than for several CPS-2 fighters. In cps2recomp's attract-mode census AvP hands frames over in the VBLANK interrupt, writes palette inline at 000EC4, and uses **no raster IRQ**, and 4,000 attract frames hash identically between its native renderer and its board model ([NATIVE_VIDEO.md](https://github.com/tmcleroy/cps2recomp/blob/main/docs/NATIVE_VIDEO.md)). Gameplay raster use is unconfirmed. Sound can keep the Z80 driver and feed a QSound HLE. MAME's `qsoundhle.cpp` and ValleyBell's qsound-hle are BSD-3 but MAME's device still loads the DL-1425 DSP ROM, whereas cps2recomp substitutes a computed equal-power pan curve ([qsoundhle.cpp](https://github.com/mamedev/mame/blob/master/src/devices/sound/qsoundhle.cpp); [cps2recomp qsound.cpp](https://github.com/tmcleroy/cps2recomp/blob/main/sound/qsound.cpp)). Timing fidelity is unproven for AvP. cps2recomp's default mode lets the 68000 do about a third more work per frame than the board, and its cycle model was compared against jtcps2 for SFA2 only ([TIMING.md](https://github.com/tmcleroy/cps2recomp/blob/main/docs/TIMING.md)).

The Wayland layer is a solved problem through SDL 3. SDL 3 selects native Wayland when the compositor exposes `wp_fifo_manager_v1` and otherwise falls back to XWayland ([SDL_waylandvideo.c](https://github.com/libsdl-org/SDL/blob/main/src/video/wayland/SDL_waylandvideo.c)). Mutter 51, KWin 6.7, Weston 15 and Hyprland 0.52 all expose fifo-v1, while KWin 6.7 lacks commit-timing-v1 and Mutter lacks tearing-control ([wayland-explorer kwin.json](https://github.com/vially/wayland-explorer/blob/main/src/data/compositors/kwin.json); [mutter.json](https://github.com/vially/wayland-explorer/blob/main/src/data/compositors/mutter.json)). SDL 3 audio prefers PipeWire ([SDL_audio.c](https://github.com/libsdl-org/SDL/blob/main/src/audio/SDL_audio.c)). cps2recomp already uses SDL_GPU (Vulkan on Linux), SDL gamepads and RetroArch-format shaders ([TOOLKIT.md](https://github.com/tmcleroy/cps2recomp/blob/main/docs/TOOLKIT.md)) but does not mention Wayland explicitly. The 59.637 Hz refresh against 60 Hz panels repeats one frame about every 2.75 s under FIFO vsync (inference from the 0.363 Hz difference), so the options are VRR pacing, running 0.6% fast with dynamic audio resampling, or tearing-control where available.

## Legal exposure concentrates in distributed binaries and the key file

No Capcom takedown of a disassembly, decompilation or recompilation was found. Capcom's two GitHub DMCA notices targeted a Mega Man Battle Network fan game (2020) and a Dragon's Dogma Online translation (2025) ([2020-01-10-capcom.md](https://github.com/github/dmca/blob/master/2020/01/2020-01-10-capcom.md); [2025-01-30-capcom.md](https://github.com/github/dmca/blob/master/2025/01/2025-01-30-capcom.md)). Capcom forced a "SEGA VS CAPCOM" fan game offline in September 2026 over character use, per search snippets ([Time Extension](https://www.timeextension.com/news/2026/09/sega-vs-capcom-fan-project-shut-down-for-using-capcoms-characters-and-likeness)). Across publishers, enforcement has targeted distributed playable builds and assets, as with Nintendo's 2020 actions against SM64 PC-port executables while the `n64decomp/sm64` repo remained, and Take-Two's re3/reVC suit, dismissed in April 2023 on undisclosed terms ([GameSpot](https://gamespot.com/articles/nintendo-is-trying-to-shut-down-that-super-mario-6/1100-6477117/); [PC Gamer](https://www.pcgamer.com/take-two-dismisses-lawsuit-against-grand-theft-auto-modders)). Sega v. Accolade covered intermediate copying for interoperability, not publication of an annotated disassembly ([Justia](https://law.justia.com/cases/federal/appellate-courts/F2/977/1510/305345/)).

AvP carries a second rights layer, with the Alien and Predator IP outside Capcom. Ownership by 20th Century Studios is asserted in project disclaimers but was not verified against a primary source ([cps2recomp avsp README](https://github.com/tmcleroy/cps2recomp/blob/HEAD/games/avsp/README.md)). cps2recomp forbids committing anything from or generated from a game, any key, or any pointer to ROM sources, yet its documentation states that release binaries contain translated game code, "a risk the maintainer has accepted (2026-10-12)" ([CONTRIBUTING.md](https://github.com/tmcleroy/cps2recomp/blob/main/CONTRIBUTING.md); [RELEASING.md](https://github.com/tmcleroy/cps2recomp/blob/main/docs/RELEASING.md)). ffight-disasm already follows the stricter model, git-ignoring `src/` as "private repo only" ([.gitignore](https://github.com/cerroverb/ffight-disasm/blob/677ddd11232d47faa14c0cfcf1f4e04f56063a25/.gitignore)). For AvP the CPS2 key adds a policy question, because the re-encrypt step needs the 20-byte key (or the derived master key and limit) at build time, and the key is part of the ROM set. Treating it like the ROM (user-supplied, never committed) preserves the existing posture (inference). Reusing cps2recomp code or its names header binds a project to GPL-3.0-only, which is compatible with ffight-disasm's GPLv3. Addresses as facts can be re-derived independently, with attribution for anything copied.

## Recommended path

The sequence below builds on existing assets, keeps every stage verifiable, and defers the native runtime decision until the disassembly yields something cps2recomp cannot (inference throughout, grounded in the sources above).

| Phase | Work | Exit criterion |
|---|---|---|
| 0. Reference | Build cps2recomp `avspu` locally from own ROM and key; run it under a Wayland session with `SDL_VIDEO_DRIVER` unset and confirm native Wayland | Playable reference binary; `make check` passes |
| 1. Cipher | Port MAME `cps2_decrypt` and `init_cps2crypt` (BSD-3) to a standalone tool; add inverse FN2; derive AvP upper limit from the key | `decrypt(encrypt(x)) == x` for all words; decrypted image matches MAME `saveo` dump |
| 2. PC-relative test | Diff MAME `saveo` vs `save` at one AvP `move.w (T,pc,dN.w)` jump table | Known whether table words are ciphered |
| 3. Generator | Pick `avspu` to align addresses with cps2recomp; add dual buffers, opcode bitmap, CPS2 `hardware.txt`, 4-chip combiner and SHA-1 table; extend jump-table follower to `aN`, `.l` and pointer-table dispatch | `make verify` prints OK for all four chips |
| 4. Coverage | Port `bot.lua` to AvP ports and RAM; trace all four characters and three-player runs; seed `entry_points.txt` from cps2recomp's documented routine addresses | Coverage of traced PCs at 0 FAIL; instruction count approaching 82,889 |
| 5. Anti-cheat | New mutation anchors plus a code/data mislabel mutation; add CI that runs `make verify` without ROM via a private runner or local hook | All mutations fail, clean source passes |
| 6. Z80 | Separate disassembly of `avp.01` (unencrypted), SHA-1 verified | Byte-identical Z80 chip |
| 7. Semantics | Name routines and RAM using mame-rr, FBNeo cheats and cps2recomp `avsp.h` with attribution; keep generated source in a private `avsp-disasm-src` repo | Named player, enemy, camera, attract, sound-command and EEPROM code |
| 8. Port | Contribute names, hand rewrites, play-testing and ending coverage to cps2recomp, or build a separate SDL 3 runtime only for a differentiator (readable C decomp in the tmntarcade style, widescreen using the mapped camera limits, three-player netplay, no distributed binaries) | Decision recorded against cps2recomp's feature set |

Phase 0 matters because cps2recomp's per-frame hashes and its interpreter provide a ready differential oracle for any later native code, and duplicating its board model gains nothing until a differentiator requires it. Phases 1 to 3 hold all the CPS2-specific risk. Phase 8's cheapest variant adds value immediately, since cps2recomp's AvP lacks hand play-testing, endings and audio review.

## Conclusion

The question has shifted from feasibility to differentiation. A native Linux AvP exists, so a second port justifies itself only through readability, extensibility or legal posture, and the byte-identical disassembly is the asset that supports all three. CPS2 encryption, which looks like the main obstacle, turns into a verification advantage once an encryptor exists, because every code/data classification error becomes a SHA-1 failure instead of a silent mislabel. The ffight-disasm design, with knowledge in small tables, generated private source and owner-guarded checkers, scales to AvP with changes concentrated in one generator and one post-link step. The unknowns are narrow and testable locally. They are the PC-relative cipher behaviour, the key's upper limit, gameplay raster use, and AvP timing fidelity, and none of them requires anything beyond the user's own ROM set and MAME.
