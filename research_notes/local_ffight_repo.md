## Q1. Repository architecture, methodology and what each tool does

### Takeaway
The repo is a small (about 1,155 lines of code, 11 commits made on 2026-11-08) toolchain that generates a byte-identical, reassemblable GNU-as 68000 source for Final Fight from the user's own ROM, using its own Python 68000 decoder, recursive-descent code discovery seeded by the vector table, MAME execution traces, manual entry points and PC-relative jump tables, plus a three-layer anti-cheat verification (per-chip SHA-1, trace-coverage from the assembler listing, mutation tests). A MAME Lua bot plays the game under the debugger `trace` command to collect more executed PCs. The generated source itself is kept out of the public repo.

**`tools/dis68k.py` (68000 decoder)**
- `decode(mem, pc)` returns an `Ins` (pc, length, text, flow in {next, stop, branch, call, jump, cond}, code `targets`, `refs` for label substitution) or `None` for an invalid 68000 instruction; output is GNU as Motorola syntax for `--register-prefix-optional` with every operand size explicit "so the assembler has no encoding choices to make" — [R/tools/dis68k.py L1-L8, L31-L38](https://github.com/cerroverb/ffight-disasm/blob/677ddd11232d47faa14c0cfcf1f4e04f56063a25/tools/dis68k.py#L1-L38).
- Strictly 68000: rejects 68020 brief-extension bits (`e & 0x0700`), 68020 long branches (`disp == 0xFF`), `cmpi` to PC-relative, line A / line F opcodes — [R/tools/dis68k.py L135-L136, L231-L232, L346-L347, L424](https://github.com/cerroverb/ffight-disasm/blob/677ddd11232d47faa14c0cfcf1f4e04f56063a25/tools/dis68k.py#L133-L140).
- Branch/PC-relative targets are emitted as placeholders `CODE_xxxxxx` / `PCREL_xxxxxx` for later label resolution; absolute `.w`/`.l` operands are recorded as `absw`/`absl` refs — [R/tools/dis68k.py L109-L130, L332, L353-L356](https://github.com/cerroverb/ffight-disasm/blob/677ddd11232d47faa14c0cfcf1f4e04f56063a25/tools/dis68k.py#L109-L130).
- `jmp`/`jsr` through an absolute or `(d16,pc)` target record that target; register-indirect `jmp` is flow "stop" (no target) — [R/tools/dis68k.py L313-L322](https://github.com/cerroverb/ffight-disasm/blob/677ddd11232d47faa14c0cfcf1f4e04f56063a25/tools/dis68k.py#L313-L322).
- The decoder reads the opcode word and all extension words from the same `mem` buffer (`D.w()` reads `self.mem`) — [R/tools/dis68k.py L45-L57](https://github.com/cerroverb/ffight-disasm/blob/677ddd11232d47faa14c0cfcf1f4e04f56063a25/tools/dis68k.py#L45-L57).

**`tools/gen.py` (source generator)**
- Usage `gen.py ROM OUT.s`; entries = every vector 1..255 that is even, `>= 0x400` and inside the image, plus `tools/entry_points.txt`, plus every PC in every `traces/*.txt` — [R/tools/gen.py L29-L48](https://github.com/cerroverb/ffight-disasm/blob/677ddd11232d47faa14c0cfcf1f4e04f56063a25/tools/gen.py#L29-L48).
- Recursive descent with a per-byte `owner[]` array; a path stops (and is logged in `bad_paths`) on an invalid decode or overlap with an existing instruction — [R/tools/gen.py L99-L123](https://github.com/cerroverb/ffight-disasm/blob/677ddd11232d47faa14c0cfcf1f4e04f56063a25/tools/gen.py#L99-L123).
- Jump tables: a `jmp|jsr (T,pc,dN.w)` whose preceding instruction is `move.w (T,pc,dN.w),dN` with the same table makes T a word-offset table; it ends at the lowest target, at the next referenced address, at 256 entries, or at a target that fails `plausible_code` (up to 4 sequential valid decodes or known code) — [R/tools/gen.py L57-L94, L126-L142](https://github.com/cerroverb/ffight-disasm/blob/677ddd11232d47faa14c0cfcf1f4e04f56063a25/tools/gen.py#L57-L142).
- Discovery is re-run from scratch up to 10 times with the previous pass's referenced addresses as table bounds, until the reference set stops growing — [R/tools/gen.py L145-L168](https://github.com/cerroverb/ffight-disasm/blob/677ddd11232d47faa14c0cfcf1f4e04f56063a25/tools/gen.py#L145-L168).
- Naming: `tools/names.txt` names applied to ROM addresses; auto labels `loc_XXXXXX` (code) / `dat_XXXXXX` (data); `tools/hardware.txt` + `tools/ram.txt` emitted as `.equ` and substituted for absolute long operands only; absolute word refs below 0x8000 get labels — [R/tools/gen.py L171-L234](https://github.com/cerroverb/ffight-disasm/blob/677ddd11232d47faa14c0cfcf1f4e04f56063a25/tools/gen.py#L171-L234).
- Emission: 256-entry vector table as `.long` (labels where the vector points to code), jump tables as `.short label-table`, unreached bytes as `.byte` lines of 16 — [R/tools/gen.py L245-L290](https://github.com/cerroverb/ffight-disasm/blob/677ddd11232d47faa14c0cfcf1f4e04f56063a25/tools/gen.py#L245-L290).
- Round-trip check: emits with `.org` before each instruction, assembles, links at 0, compares each instruction's bytes to the ROM; any mismatch or assembler error becomes a raw `.short` line tagged `[raw: assembler re-encodes]` with the instruction in a comment, iterated up to 10 passes; results in `build/fallback.txt`, `build/jump_tables.txt`, `build/bad_paths.txt` and printed stats (instructions, code bytes, fallbacks, labels, jump tables, bad paths, unlabelable refs) — [R/tools/gen.py L293-L355](https://github.com/cerroverb/ffight-disasm/blob/677ddd11232d47faa14c0cfcf1f4e04f56063a25/tools/gen.py#L293-L355).
- Hard-coded Final Fight bits in gen.py: output header "Final Fight (World, MAME set ffight) 68000 program" and the "% of 1 MiB" stat label; image size is otherwise taken from the input length (`SIZE = len(rom)`) — [R/tools/gen.py L22, L246, L347](https://github.com/cerroverb/ffight-disasm/blob/677ddd11232d47faa14c0cfcf1f4e04f56063a25/tools/gen.py#L246).

## Q3. Verification approach: `verify/` and CODEOWNERS

### Takeaway
Verification has four layers: SHA-1 per rebuilt program chip, a trace-based coverage check that reads the assembler's own listing (so code cannot hide as `.byte`), an objdump cross-check that raw-word fallbacks really are single instructions, and a mutation test proving the checks fail on five kinds of cheating. CODEOWNERS assigns `/verify/`, `/Makefile`, `/traces/` and `/.github/` to `@cerroverb`, i.e. the verification inputs are owner-reviewed.

### Cited Findings
- `make verify` runs `verify_maincpu.py build/ffight.bin` then `check_coverage.py build/ffight.lst traces/*.txt`, both with `python3 -I`; the build reads only `src/` — [R/Makefile L1, L18-L20](https://github.com/cerroverb/ffight-disasm/blob/677ddd11232d47faa14c0cfcf1f4e04f56063a25/Makefile#L18-L20).
- `verify_maincpu.py`: requires exactly 0x100000 bytes, splits into the five chips (even/odd bytes of 0x00000-0x3FFFF and 0x40000-0x7FFFF, word-swapped 0x80000-0xFFFFF) and compares SHA-1 with values copied from MAME `ROM_START( ffight )` — [R/verify/verify_maincpu.py L1-L22](https://github.com/cerroverb/ffight-disasm/blob/677ddd11232d47faa14c0cfcf1f4e04f56063a25/verify/verify_maincpu.py).
- `check_coverage.py`: parses the `as -al` listing (independent of gen.py), classifies each byte as start/inside of instruction, raw fallback or data; fails if any traced PC is not the start of an instruction or raw line; raw lines only count if `objdump -D -b binary -m m68k:68000` decodes them as exactly one instruction of the same length — [R/verify/check_coverage.py L1-L75](https://github.com/cerroverb/ffight-disasm/blob/677ddd11232d47faa14c0cfcf1f4e04f56063a25/verify/check_coverage.py).
- `mutation_test.sh` copies `src`, `Makefile`, `verify`, `traces` to a temp dir and requires all five mutations to fail and the unmodified source to pass: (1) change an immediate `#0x3ffb`→`#0x3ffc`; (2) replace `moveq #0,d1` with identical `.byte 0x72,0x00`; (3) whole program as `.incbin "rom/maincpu.bin"`; (4) strip `[raw:` tags; (5) via `m5.py`, disguise two instructions (`0x7200,0x20c1`) as one fake raw instruction and redefine `loc_000412` — [R/verify/mutation_test.sh L1-L39](https://github.com/cerroverb/ffight-disasm/blob/677ddd11232d47faa14c0cfcf1f4e04f56063a25/verify/mutation_test.sh), [R/verify/m5.py L1-L9](https://github.com/cerroverb/ffight-disasm/blob/677ddd11232d47faa14c0cfcf1f4e04f56063a25/verify/m5.py).
- README states `make verify` "must print `OK` for all five chips and `NOT covered by an instruction (FAIL): 0`" — [R/README.md L29-L35](https://github.com/cerroverb/ffight-disasm/blob/677ddd11232d47faa14c0cfcf1f4e04f56063a25/README.md#L29-L35).
- CODEOWNERS: `/verify/ @cerroverb`, `/Makefile @cerroverb`, `/traces/ @cerroverb`, `/.github/ @cerroverb` — [R/.github/CODEOWNERS L1-L4](https://github.com/cerroverb/ffight-disasm/blob/677ddd11232d47faa14c0cfcf1f4e04f56063a25/.github/CODEOWNERS). Commit message: "Add CODEOWNERS for the verification files" (`c354f7c`).
- There is no CI workflow in `.github/` (CODEOWNERS is the only file there) — local `find`.

### Inferences
- The design guards against an automated agent (or anyone) "passing" by copying ROM bytes: the build never reads the ROM, the coverage check uses the assembler's listing rather than the generator's claims, and CODEOWNERS protects the checkers and trace inputs from being weakened in a PR. The `handoff/` ignore entry and the `claude/...` branch name suggest the repo is worked on by AI agents under owner review.
- The mutation anchors (`#0x3ffb`, `loc_000412`, `moveq #0,d1`) are Final Fight-specific and need new anchors for AvP; the mechanism is reusable.

### Gaps
- Whether GitHub branch protection actually requires code-owner review on `main` could not be checked (gh was restricted to search). Without that setting, CODEOWNERS only requests reviews.
- No CI runs `make verify`; verification relies on local runs.

## Q4. Current progress (quantified)

### Takeaway
The README claims the generated source rebuilds all five program chips byte-identically. Committed knowledge is small: 72 label names (18 of them string labels), 35 hardware symbols, 5 RAM names, 1 manual entry point and one 120-second attract-mode trace with 9,342 unique executed PCs. ## Q5. Transferability to an Alien vs. Predator (CPS2, `avsp`) disassembly and Linux/Wayland native port

### Takeaway
The 68000 decoder, label/naming machinery, trace collector, coverage checker, mutation-test idea and bot framework transfer almost unchanged. The ROM combiner, SHA-1 table, hardware symbol table, bot RAM addresses/port tags and trace script need straightforward per-game edits. The real new work is CPS2 opcode encryption: instructions must be decoded from a decrypted opcode image while data comes from the raw image, and a byte-identical rebuild needs a re-encryption step for instruction words only. CPS1-specific symbols (CPS-B 04 IDs, DIP ports, YM2151/OKI sound) don't apply.

### Cited Findings
**AvP ROM set facts (MAME)**
- `avsp` = "Alien vs. Predator (Europe 940520)", machine `cps2`, inputs `cps2_3p3b`, init `init_cps2`; clones `avspu` (USA), `avspj`, `avspa`, `avsph` and the bootleg `avspd` (Phoenix Edition, machine `dead_cps2`) — [MAME cps2.cpp L12599-L12603, L12855](https://github.com/mamedev/mame/blob/master/src/mame/capcom/cps2.cpp#L12599-L12603).
- Program ROM: four 0x80000 chips, each `ROM_LOAD16_WORD_SWAP`, contiguous: `avpe.03d` (SHA1 f60b0e39139ea40e0b0ba97ed01d4a757ed65e1a) @0x000000, `avpe.04d` (930f02e4d35686e80fbdd673380c4b2bd784a9e5) @0x080000, `avp.05d` (5549bc9d780753bc9c10fba82588e5c3d4a2acb2) @0x100000, `avp.06` (9bcfc0a015ffba9cdac25b6270939a9690de5da7) @0x180000, i.e. 2 MiB of 68000 program; plus Z80 `avp.01`, QSound samples `avp.11m`/`avp.12m`, 8 GFX chips, and the 20-byte `avsp.key` — [MAME cps2.cpp L2497-L2524](https://github.com/mamedev/mame/blob/master/src/mame/capcom/cps2.cpp#L2497-L2524). `CODE_SIZE` is 0x400000 — [MAME cps2.cpp L646](https://github.com/mamedev/mame/blob/master/src/mame/capcom/cps2.cpp#L646).
- `avspd` replaces `avpe.03d`, `avpe.04d` and `avp.06` with `avped.03d`, `avped.04d`, `avpd.06` but keeps `avp.05d`, and uses `phoenix.key` — [MAME cps2.cpp L11161-L11188](https://github.com/mamedev/mame/blob/master/src/mame/capcom/cps2.cpp#L11161). MAME notes Phoenix sets were hand-modified "to correctly contain only decrypted code and data, as well as modification to compensate for the memory map changes" and "there were sometimes errors introduced" — [MAME cps2.cpp L11035-L11044](https://github.com/mamedev/mame/blob/master/src/mame/capcom/cps2.cpp#L11035-L11044).

**CPS2 encryption (the main adaptation)**
- "The encryption only affects opcodes, not data. It consists of two 4-round Feistel networks ... and involves both the 16-bit opcode and the low 16 bits of the address"; the covered address range differs per game; a watchdog opcode must run periodically or decryption is disabled — [MAME cps2crypt.cpp header](https://github.com/mamedev/mame/blob/master/src/mame/capcom/cps2crypt.cpp). MAME's Phoenix notes describe original ROMs as "encrypted code mixed with decrypted data" — [MAME cps2.cpp L11040-L11041](https://github.com/mamedev/mame/blob/master/src/mame/capcom/cps2.cpp#L11040-L11041).
- MAME decodes the key into a 64-bit master key, three watchdog-instruction words, and an upper limit `upper = (((~decoded[9] & 0x3ff) << 14) | 0x3fff) + 1`, `lower = 0` (dead board: only 0xFF0000-0xFFFFFF) — [MAME cps2.cpp L10893-L10931](https://github.com/mamedev/mame/blob/master/src/mame/capcom/cps2.cpp#L10893-L10931). `cps2_decrypt` fills `dec[a]` with the FN2 output for words inside the range and copies `rom[a]` otherwise — [MAME cps2crypt.cpp L635-L712](https://github.com/mamedev/mame/blob/master/src/mame/capcom/cps2crypt.cpp#L635-L712).
- The decrypted image is mapped as the 68000's `AS_OPCODES` space (`decrypted_opcodes_map`, 0x000000-0x3FFFFF), separate from `AS_PROGRAM` — [MAME cps2.cpp L1316-L1319, L1740-L1744](https://github.com/mamedev/mame/blob/master/src/mame/capcom/cps2.cpp#L1316-L1319). MAME's 68000 core keeps separate `m_program`/`m_opcodes` accessors — [MAME m68000.h L154-L161](https://github.com/mamedev/mame/blob/master/src/devices/cpu/m68000/m68000.h#L154-L161).
- Repo dependency: `dis68k.decode(mem, pc)` reads opcode and extension words from one buffer ([R/tools/dis68k.py L45-L57](https://github.com/cerroverb/ffight-disasm/blob/677ddd11232d47faa14c0cfcf1f4e04f56063a25/tools/dis68k.py#L45-L57)); gen.py uses one `rom` buffer for decoding, jump-table words, `.byte` data and the round-trip comparison ([R/tools/gen.py L20, L82, L287, L331](https://github.com/cerroverb/ffight-disasm/blob/677ddd11232d47faa14c0cfcf1f4e04f56063a25/tools/gen.py#L331)).

**Memory map / hardware differences (CPS1 `ffight` vs CPS2)**

### Inferences
- Byte-identical CPS2 rebuild pipeline (proposal): assemble → plaintext image P → for every word that the assembler listing marks as instruction or raw-fallback and that lies below the key's upper limit, apply the inverse of MAME's FN2 for that address (a Feistel network is invertible given the same subkey) → split into four word-swapped chips → SHA-1 against MAME. Data and unreached bytes are emitted from the raw image, so they need no transform. This keeps the repo's "the build never reads the ROM" property only if the 20-byte key (or derived master key and limit) is supplied to the build, which needs a policy decision since it's part of the ROM set.
- Encryption also gives a strong anti-cheat signal: a word mislabelled as data versus code produces wrong ciphertext and fails SHA-1, so the coverage check gets an extra independent cross-check.
- Using `avspd` (Phoenix, plaintext) as a decoding shortcut is possible for exploration, but MAME notes Phoenix sets are modified and can contain errors, so `avsp` + key decryption should stay the reference; `avp.05d` is shared between both sets, which allows a direct comparison for the 0x100000-0x17FFFF range.
- For a native Linux/Wayland port, the FF repo offers only the disassembly half. It has no static recompiler, no C translation and no CPS-A/CPS-B/object/QSound renderer or audio runtime. Those would have to come from elsewhere; the ReXGlue-based Linux ports (Q6) are the closest in-house precedents.
- The bot's MAME-trace approach is likely more valuable on AvP than on FF, because the decrypted-range boundary and code mixed with data make pure static recursive descent riskier. Traces that cover all three characters (and the 3-player paths, via `-autoboot_script` controlling P1-P3) would seed discovery.

### Gaps
- Whether PC-relative operand reads (e.g. `move.w (T,pc,d0.w),d0` jump-table loads) on CPS2 go through the decrypted or raw view was not verified in the MAME 68000 core or on hardware. This decides which buffer gen.py's jump-table follower must read; it must be checked (e.g. by tracing a known jump table) before porting `jump_table_targets`.
- AvP's encrypted-range upper limit and watchdog instruction require the key file; not examined (no ROMs downloaded).
- No inverse-FN2 (encryption) implementation was located in MAME (it only decrypts); one must be written or found.
- Whether MAME's debugger `trace` on CPS2 disassembles from the decrypted space (it should, since `AS_OPCODES` is mapped) was not tested; only the PC field is used by `collect_pcs`, so this matters only for human reading of traces.
