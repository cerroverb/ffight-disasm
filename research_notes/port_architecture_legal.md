# Alien vs. Predator (CPS2) native Linux/Wayland port: architecture options, platform layer, legal constraints

Research date: 2026-11-09. Method: web search and fetches of primary sources (GitHub READMEs and docs, MAME and SDL source, the github/dmca repo). These hosts were blocked in this session and could not be fetched directly: en.wikipedia.org, wayland.app, torrentfreak.com, kotaku.com and limitedrungames.com. Findings from those hosts come from search-result snippets and are labelled "(snippet only)". "Verified" below means the claim was read in a fetched primary source. Nothing here is legal advice.

**The most important finding.** A static-recompilation port of this game already exists. **CPS-2 Recomp** (github.com/tmcleroy/cps2recomp, GPL-3.0-only, beta) ships "Alien vs. Predator Recomp" built from the `avspu` (USA 940520) set, for Linux, macOS, Windows and SteamOS, on SDL 3. Its AvP progress page is dated 2026-10-18. This changes the starting point: any new AvP port competes with, or could build on, a working toolkit that already does strategy (b) with full hardware HLE.

---

## 1. Port strategies and precedents (manual reimplementation, static recompilation, interpreter shim, matching decompilation); feasibility for hand-written 68000 code

### Takeaway
Static recompilation of 68000 to C/C++ with a hand-written board model is now a proven approach for CPS2. CPS-2 Recomp covers 22 CPS-2 games plus CPS-1 titles, AvP among them, and solves the hard parts of hand-written 68k code: finding code, jump tables, interrupts at block boundaries, timing, and an interpreter fallback for unfound code. Manual reimplementation in the style of Cannonball gives the most freedom to change the game but costs years. An interpreter shim is the cheapest to get running. Matching decompilation does not apply to hand-written assembly and has no known toolchain behind it.

### Cited Findings

**(b) Static recompilation, the direct precedent: CPS-2 Recomp**
- CPS-2 Recomp describes itself as "Unofficial native PC ports of Capcom's CPS-2 arcade games (and a CPS-1 one)… Each game's program is translated ahead of time into C++ and runs on a machine written for this project, not an emulator." Platforms: macOS, Linux (Steam Deck and ARM64), Windows and Android. GPL-3.0-only. The GitHub page showed 724 commits, 171 stars and a "Beta" label. — [cps2recomp README](https://github.com/tmcleroy/cps2recomp)
- AvP is in the list as "Alien vs. Predator (1994) | avspu (USA 940520) | Beat-'em-up: three players, a stage to start at, score attack". The other regional sets of the same release (avsp Europe, avspj, avspa, avsph, all 940520) run on the same translation, "each as the board plays in its region". Older dumps without the key file, or with old `avp.14m/16m/18m/20m` graphics ROMs, are rejected. — [cps2recomp games/avsp/README.md](https://github.com/tmcleroy/cps2recomp/blob/main/games/avsp/README.md)
- AvP status on 2026-10-18: "`make explore` found the code (82,889 instructions; none left to the interpreter but 25 a guess took for code); the sound program, Capcom's QSound driver of November 1993, is translated too (2,153 instructions). `make check` passes." The README adds: "Beta. The game plays through its first rounds in made-up play… but nobody has played it by hand yet." Open items include two unplaced music cues, endings not reached, and the sound "has not been listened to". — [games/avsp/PROGRESS.md](https://github.com/tmcleroy/cps2recomp/blob/main/games/avsp/PROGRESS.md); [games/avsp/README.md](https://github.com/tmcleroy/cps2recomp/blob/main/games/avsp/README.md)
- How it works. `tools/recomp.py` translates the 68000 program and `tools/recompz80.py` the Z80 program. Code is found "by reading the program and by made-up play (`tools/explore.sh`)". "Code it has not found yet runs in an interpreter, and is counted, so that the count can be driven to zero." Hand-written "readable rewrites" of routines are checked against the original on every call (memory, registers, timing, and video RAM when asked). — [docs/TOOLKIT.md](https://github.com/tmcleroy/cps2recomp/blob/main/docs/TOOLKIT.md)
- Verification. One interpreter (`machine/m68k.cpp`) and the translated code share the flag routines and count the same cycles. `make check-blocks` runs each translated block beside the interpreter and compares registers, flags, cycle count, branch target and the ordered list of memory writes. `make check` compares per-frame state hashes across run modes. — [docs/VERIFYING.md](https://github.com/tmcleroy/cps2recomp/blob/main/docs/VERIFYING.md)
- Interrupts and divergence. "The interpreter takes interrupts between instructions, translated code between blocks, and where a game's frames fill the processor that moves when a task gives way and so the random number (Alpha, Alpha 2 and Super Turbo part for good within the ladder, #190)." A build with no translated code is therefore not frame-identical to the translated build. — [docs/VERIFYING.md](https://github.com/tmcleroy/cps2recomp/blob/main/docs/VERIFYING.md)
- Code discovery is not finished by static analysis alone. "With different timing a game can also reach code its exploration never did (Super Puzzle Fighter II Turbo jumped into what the translator had taken for data): the interpreter runs it, and `--record-entries` adds it for the next translation." — [docs/TIMING.md](https://github.com/tmcleroy/cps2recomp/blob/main/docs/TIMING.md)
- Jump tables are handled by walking them. The toolkit's port-mapping tool walks "both programs' code… side by side from the anchors and from jump tables". The CPS2 key ciphers PC-relative data reads, which mattered for one jump table ("a Super Turbo jump table at 06CCB2 read past its end"). — [docs/TOOLKIT.md](https://github.com/tmcleroy/cps2recomp/blob/main/docs/TOOLKIT.md)
- Same approach in this repo. The local ffight-disasm README (this repository) finds code "through jump tables of the form `move.w (T,pc,d0.w),d0; jmp (T,pc,d0.w)`", as well as by recursive descent and from MAME traces. — /home/user/ffight-disasm/README.md (local)

**(b) Other static recompilers, general and 68000-specific**
- N64Recomp: "a tool to statically recompile N64 binaries into C code". Translation is "very literal"; `jal` becomes a function call; the tool tries to turn `jr` into a switch when it detects a jump table; function pointers become `LOOKUP_FUNC(...)` runtime lookups. It "has mostly been tested on binaries built with old MIPS compilers (e.g. mips gcc 2.7.2 and IDO)". — [N64Recomp README](https://github.com/N64Recomp/N64Recomp)
- XenonRecomp (Xbox 360 to C++) says it was "heavily inspired by N64: Recompiled". It has no generic jump-table solution ("there is no fully generic solution for handling jump tables"), MMIO is "currently unimplemented", and exceptions are unsupported. Jump tables come from an analyzer and a TOML file. — [XenonRecomp README](https://github.com/hedge-dev/XenonRecomp)
- ReXGlue is described as the successor toolkit to XenonRecomp. — [ReadOnlyMemo interview](https://readonlymemo.com/rexglue-xbox-360-recompilation-interview/) (snippet only)
- 68000-specific recompilers exist. PixelSorcery rebuilds Genesis 68000 and Z80 code as C and checks each port against Genesis Plus GX "at every controller poll"; unreached code falls back to an interpreter. segagenesisrecomp (Genesis 68K to C, clean-room runtime, Z80 experimental) keeps its shared decoder in m68k-recomp-core. amiga-recomp turns Amiga 68000 code into C++20. amiga-re-kit (AREK) does ahead-of-time C/WASM, checked against vAmiga. convert68000toc transpiles Amiga assembly source. — [pixel_sorcery](https://github.com/nico3185/pixel_sorcery); [segagenesisrecomp](https://github.com/TechnicallyComputers/segagenesisrecomp); [m68k-recomp-core](https://github.com/geno55/m68k-recomp-core); [amiga-recomp](https://github.com/retro-foundry/amiga-recomp); [amiga-re-kit](https://pypi.org/project/amiga-re-kit/1.0.18/); [convert68000toc](https://bitbucket.org/rhinoid/convert68000toc/src/main/) (search descriptions; READMEs not fetched)

**(a) Manual reimplementation in C/C++**
- Cannonball (OutRun): "The original 68000 and Z80 assembler code has been rewritten in C++. This makes it possible to make improvements suitable for modern platforms, including a higher frame-rate and widescreen support. It requires the original ROMs, as these contain elements including the graphics and audio data." It uses SDL 2 and Boost and is maintained by Chris White. — [djyt/cannonball](https://github.com/djyt/cannonball)
- Effort indicator for Cannonball: the release announcement calls it the product of "many years of reverse engineering, hacking and debugging". A fan post says about 3 years. Public release was around 2 December 2012. — [shmups.system11 thread](https://shmups.system11.org/viewtopic.php?p=857570); [Sonic Retro post](https://forums.sonicretro.org/goto/post?id=724150) (snippets only)
- sf2platinum: the GitHub repo `sf2platinum/sf2platinum` now holds a single commit with an empty README (1 star, no license). The account also has a ROM-merge gist. Search results connect it to `bentorkington/sf2ww`, described as "A clone of Street Fighter 2 World Warrior, written from scratch in C + OpenGL". That repo returned 404/403 when fetched on 2026-11-09. — [sf2platinum repo](https://github.com/sf2platinum/sf2platinum); [sf2platinum gist](https://gist.github.com/sf2platinum/19adb572afe948c3e51f24727dc44a38); [sf2ww (search listing)](https://github.com/bentorkington/sf2ww)

**(c) Interpreter shim (original code in an embedded 68000 core, native HLE for the hardware)**
- Musashi: "a Motorola 68000, 68010… emulator written in C… It has been successfully running in the MAME project… for years". MIT-style permissive license. — [Musashi readme](https://github.com/kstenerud/Musashi)
- Moira: "The core emulator (Moira) is published under the terms of the MIT license." — [Moira LICENSE](https://github.com/dirkwhoffmann/Moira)
- CPS-2 Recomp is in part a hybrid. Its interpreter runs unfound code, and other games' boards ("guests") run fully on the interpreter with hooks at known addresses (`AddGuestHook`). An interpreted 68000 with HLE hooks is therefore already used in production there. — [docs/TOOLKIT.md](https://github.com/tmcleroy/cps2recomp/blob/main/docs/TOOLKIT.md)
- Performance budget: "On the Steam Deck a frame is about 2–2.5 ms… drawing is three quarters of a frame." — [docs/VERIFYING.md](https://github.com/tmcleroy/cps2recomp/blob/main/docs/VERIFYING.md)

**(d) Matching decompilation, and what is known of Capcom's tools**
- No primary source was found on Capcom's CPS1/CPS2-era programming language or toolchain. Secondary sources say Capcom used the Sharp X68000 as a development machine for CPS1. A forum post says, citing a Japanese fan site, that "most CPS1 and CPS2 games were reportedly produced on that machine". — [Giant Bomb X68000](https://giantbomb.com/wiki/Platforms/Sharp_X68000); [Arcade Hacker blog](https://arcadehacker.blogspot.com.au/2015/05/); [AssemblerGames thread](https://assemblergames.org/viewtopic.php?t=3601&start=20) (snippets only)
- Evidence from the binaries of shared, versioned libraries: "Capcom's video library, which the games share" has routines with identical CRCs across ten games, and "Capcom's sound driver, version 2.01b" exists. AvP keeps its globals relative to A5 (`A5 is FF8000`). — [docs/NATIVE_VIDEO.md](https://github.com/tmcleroy/cps2recomp/blob/main/docs/NATIVE_VIDEO.md); [docs/TOOLKIT.md](https://github.com/tmcleroy/cps2recomp/blob/main/docs/TOOLKIT.md); [avsp PROGRESS.md](https://github.com/tmcleroy/cps2recomp/blob/main/games/avsp/PROGRESS.md)
- Modern CPS1 homebrew can use C: Fabien Sanglard's CCPS SDK supports 68000 assembly, Z80 assembly and C through a modern m68k gcc. It is not Capcom's tooling. — [CCPS](https://fabiensanglard.net/ccps/)

**Timing, interrupts and frame pacing**
- MAME's CPS2 driver uses a 16 MHz 68000 (`M68000(config, m_maincpu, 16_MHz_XTAL)`) and then `set_clock_scale(0.7375)` with the comment "HACK: RAM access waitstates etc. aren't emulated - slow the CPU to compensate". That gives about 11.8 MHz. The driver notes say "Various timing loops show 11.8 being the average speed". Z80 at 8 MHz with an interrupt at 8 MHz/32000 (about 250 Hz), a 93C46 EEPROM, and a per-scanline raster timer. — [MAME cps2.cpp](https://github.com/mamedev/mame/blob/master/src/mame/capcom/cps2.cpp)
- Frame rate: CPS pixel clock = 16 MHz/2, HTOTAL 512, VTOTAL 262. That is 8,000,000/(512×262) = **59.637 Hz** (computed from these constants). — [MAME cps1.h](https://github.com/mamedev/mame/blob/master/src/mame/capcom/cps1.h)
- CPS-2 Recomp's optional `arcade_timing` models the DL-1827 bus acknowledge wait (one clock per access outside 500000-7FFFFF) and the CPS-A DMA ("7 to 13% of a frame"). Without it, "the games then do about a third more work in a frame than the board lets them, and seldom slow down." With it, SFA2 work RAM matched a Verilator simulation of jotego's jtcps2 at 5,639 of 5,671 frames. Only SFA2 was compared. — [docs/TIMING.md](https://github.com/tmcleroy/cps2recomp/blob/main/docs/TIMING.md); [docs/ARCADE_ACCURACY.md](https://github.com/tmcleroy/cps2recomp/blob/main/docs/ARCADE_ACCURACY.md); [jtcores](https://github.com/jotego/jtcores)
- AvP's interrupt use (CPS-2 Recomp census, attract mode only): the frame handover is in the VBLANK interrupt (vectors at 68/70; mask 4 = VBLANK level 2, mask 10 = raster level 4). The raster-interrupt column for AvP reads "none". Marvel Super Heroes, by contrast, uses its raster IRQ (0007B6) to change scroll 2/3 and layer control mid-frame. — [docs/NATIVE_VIDEO.md](https://github.com/tmcleroy/cps2recomp/blob/main/docs/NATIVE_VIDEO.md)

### Inferences
- **Feasibility ranking for hand-written 68000 code** (my synthesis):
  - **(b) static recompilation plus HLE board.** Highest feasibility per unit of effort, because there is a direct, working precedent for this exact game. The risks it carries (unfound code, interrupt granularity, RNG divergence, timing) are documented and handled with an interpreter fallback and differential checks.
  - **(c) interpreter shim plus HLE.** The fastest path to a running native build: Musashi or Moira are MIT, and the CPU load is trivial. It keeps exact interrupt semantics but makes deep modding harder.
  - **(a) manual reimplementation.** Most flexible (widescreen, higher frame rate, as in Cannonball), but measured in years for one person. It is best done *incrementally* on top of (b) or (c), replacing routines one at a time with differential checks, which is CPS-2 Recomp's "readable rewrites" model.
  - **(d) matching decompilation.** Not applicable. With no known Capcom compiler, and most likely hand-written assembly (unverified), there is no compiler whose output can be matched. A "decompilation" here can only mean a hand translation that matches behavior, not bytes.
- Self-modifying code is probably a minor issue for CPS2. The 68000 program runs from encrypted ROM, and the opcodes are fetched through a decrypted-opcode address space (MAME maps `AS_OPCODES` separately), so code cannot modify itself in ROM. Any RAM-resident code would need detecting. No source states whether AvP copies code to RAM; CPS-2 Recomp's interpreter fallback would catch it either way.
- A byte-identical disassembly (the starting point here) gives strategies (a), (b) and (c) the same assets CPS-2 Recomp derived on its own: labels, jump-table bounds and RAM maps. It mainly speeds up naming and rewrites, and adds little to code discovery that CPS-2 Recomp has not already solved.
- Pacing at 59.637 Hz is easiest when the game loop is the master clock and audio is resampled. A native port could also offer an "exact 60 Hz" option, which runs the game 0.6% fast.

### Gaps
- Whether CPS-2 Recomp's translator handles code executed from RAM or self-modifying code: not stated in the fetched docs.
- No Hacker News thread on static recompilation was fetched. The general discussion of trade-offs relies on project READMEs.
- No primary source (interview, Capcom document) on whether CPS2-era games were written in assembly or C. The X68000 development-machine claim is secondary only.
- Exact total effort for CPS-2 Recomp (dates, person-hours) is not known. The GitHub API was rate-limited and the repo is not attached to this session, so creation and push dates could not be read.
- The sf2platinum project's original content and reason for removal are unknown.

## 2. Hardware HLE required (tilemaps, objects, palette, raster, QSound/Z80, EEPROM, 3-player inputs)

### Takeaway
Everything AvP needs has been modelled in an existing GPL project: the three scroll layers with row scroll, objects and priorities, palette pages and the VBLANK latch, a 93C46 EEPROM, players 3 and 4 at 804010, the Z80 driver translated to C++, and a QSound model based on MAME's HLE. AvP's frame handover follows the shared Capcom video library pattern, and the raster interrupt was not seen in its census. The Z80 sound program can be kept (emulated or recompiled). MAME's QSound HLE still needs the DL-1425 DSP ROM image, which CPS-2 Recomp avoids by computing approximations of the DSP tables.

### Cited Findings
- **Video boundary.** "Their main loop draws: it writes the next frame's object list into the object bank not on screen, writes the scroll screens' maps and the row-scroll table in video RAM, and writes colours into palette buffers… Then the vertical blank's interrupt hands the frame to the board in one place: the object bank swapped, the shadows copied to the CPS-A and CPS-B registers… and the palette's base written last." "Video RAM… and object memory are the game's data structures… What goes native is the board: the registers' meanings, the latching at the vertical blank, and the drawing." — [docs/NATIVE_VIDEO.md](https://github.com/tmcleroy/cps2recomp/blob/main/docs/NATIVE_VIDEO.md)
- **AvP's video routines** (census): handover at 000E0E, 001214, 0012EC; palette "inline (000EC4)"; object list built in the main loop; raster IRQ "none" (attract mode only). With CPS-2 Recomp's native renderer, AvP's 4,000 attract-mode frames hash identically to its board model. Widescreen is *not* enabled for AvP ("Without widescreen, as before (sfa2, msh, dstlk, avsp, gigawing)"). — [docs/NATIVE_VIDEO.md](https://github.com/tmcleroy/cps2recomp/blob/main/docs/NATIVE_VIDEO.md)
- **DMA and raster details** the HLE must respect: the CPS-A fetches row scroll every line, tile rows every 8 lines (scroll 1) or 16 lines (others), and up to six palette pages of 512 words (about 12,300 clocks) after the palette base write. — [docs/TIMING.md](https://github.com/tmcleroy/cps2recomp/blob/main/docs/TIMING.md)
- **MAME memory map**: QSound shared RAM at 0x618000-0x619FFF; IN2 + EEPROM at 0x804020; volume at 0x804030; EEPROM write port at 0x804040; EEPROM is `EEPROM_93C46_16BIT`. AvP sets use input layout `cps2_3p3b` (3 players, 3 buttons). — [MAME cps2.cpp](https://github.com/mamedev/mame/blob/master/src/mame/capcom/cps2.cpp)
- **Three players** in CPS-2 Recomp: "the toolkit's CPS-2 machine reads players 3 and 4 where the board has them (their sticks and buttons at 804010, Start and Coin on the system port), game.cfg says `players = 3`." AvP's player mode setting (A5+1CE) selects 3 players with separate chutes, 3 on one chute, or 2 (factory default). — [games/avsp/PROGRESS.md](https://github.com/tmcleroy/cps2recomp/blob/main/games/avsp/PROGRESS.md)
- **Settings EEPROM**: CPS-2 Recomp's 93C46 "answers at once", as in jtcps2. A real chip is busy for a few ms after writes. — [docs/TIMING.md](https://github.com/tmcleroy/cps2recomp/blob/main/docs/TIMING.md)
- **Sound: keep the Z80 or replace it.** CPS-2 Recomp keeps the Z80 *program* but translates it: AvP's "Capcom's QSound driver of November 1993" is recompiled (2,153 instructions). For games with driver v2.01b it also has a hand rewrite (`sound/driver.cpp`), checked "every chip write against the Z80's". — [avsp PROGRESS.md](https://github.com/tmcleroy/cps2recomp/blob/main/games/avsp/PROGRESS.md); [docs/TOOLKIT.md](https://github.com/tmcleroy/cps2recomp/blob/main/docs/TOOLKIT.md)
- **MAME QSound HLE** (`qsound_hle_device`, BSD-3-Clause, superctr and Valley Bell) is "Based on disassembled DSP code", but still declares a ROM region loading `dl-1425.bin` (the DSP's internal ROM, CRC d6cf5ef5). MAME's LLE `qsound` device (Vas Crabb, BSD-3-Clause) emulates the DSP16A and also loads `dl-1425.bin`. — [MAME qsoundhle.cpp](https://github.com/mamedev/mame/blob/master/src/devices/sound/qsoundhle.cpp); [MAME qsound.cpp](https://github.com/mamedev/mame/blob/master/src/devices/sound/qsound.cpp)
- **CPS-2 Recomp's QSound** "follows MAME's (superctr, Valley Bell)" but replaces the DSP ROM's pan table: "The chip has this as a table in its ROM; this is an equal-power curve." jtcps2 "cannot run its QSound without the chip's own program (not part of a ROM set)". — [cps2recomp sound/qsound.cpp](https://github.com/tmcleroy/cps2recomp/blob/main/sound/qsound.cpp); [README](https://github.com/tmcleroy/cps2recomp); [docs/TIMING.md](https://github.com/tmcleroy/cps2recomp/blob/main/docs/TIMING.md)
- **Encryption**: CPS2 program ROMs are ciphered. CPS-2 Recomp uses MAME's `cps2crypt` (BSD-3-Clause, Andreas Naive and Nicola Salmoria) with the player's own `.key` file: "no key is in this repository." — [README](https://github.com/tmcleroy/cps2recomp); [docs/TOOLKIT.md](https://github.com/tmcleroy/cps2recomp/blob/main/docs/TOOLKIT.md)

### Inferences
- The HLE workload is lower for AvP than for the Marvel games, since no raster-IRQ mid-frame scroll changes were seen. A per-frame renderer working from the VBLANK-latched shadows should be enough, though row scroll is still needed. This rests on an attract-mode-only census, so gameplay could still use the raster IRQ.
- For sound, the lowest-risk path is to keep the Z80 driver (interpreted or recompiled) and drive a QSound model. Decide early whether to require the user's `qsound.zip`/`dl-1425.bin` (MAME HLE fidelity) or use computed approximations (CPS-2 Recomp's choice, no extra file).

### Gaps
- No measured fidelity comparison between CPS-2 Recomp's approximated QSound tables and MAME's DSP-ROM-backed HLE.
- Whether AvP uses the raster IRQ or row scroll during gameplay stages: not confirmed. The census covered attract mode only.

## 3. Linux/Wayland platform layer (SDL3 vs SDL2, GLFW, raw Wayland, presentation timing, 59.63 Hz, VRR, audio, input, scaling, CRT shaders)

### Takeaway
SDL 3 is the lowest-risk stack and the one the precedent uses. CPS-2 Recomp runs on SDL 3 with SDL_GPU (Vulkan on Linux), SDL gamepads and RetroArch-format shaders. SDL 3 picks native Wayland only when the compositor exposes `wp_fifo_manager_v1`, otherwise it falls back to XWayland; current GNOME (Mutter 51), KDE (KWin 6.7), Weston 15 and Hyprland all expose fifo-v1. SDL 3's audio prefers PipeWire. Commit-timing-v1 is the protocol still missing in KWin 6.7, with a merge reported for Plasma 6.8.

### Cited Findings
- **SDL3 Wayland selection (current source).** `IsWaylandPreferred()` checks only for `wp_fifo_manager_v1`. Without it SDL logs "This compositor lacks support for the fifo-v1 protocol; falling back to XWayland for GPU performance reasons (set SDL_VIDEO_DRIVER=wayland to override)". The main branch is version 3.5.0. — [SDL_waylandvideo.c](https://github.com/libsdl-org/SDL/blob/main/src/video/wayland/SDL_waylandvideo.c); [SDL_version.h](https://github.com/libsdl-org/SDL/blob/main/include/SDL3/SDL_version.h)
- History: SDL first required both fifo-v1 and commit-timing-v1 (PR #9383). PR #11640 (December 2024) dropped commit-timing because "Mesa does not need it for FIFO behavior". — [SDL PR #11640](https://github.com/libsdl-org/SDL/pull/11640); [SDL PR #9383](https://github.com/libsdl-org/SDL/pull/9383); [ArchWiki Wayland](https://wiki.archlinux.org/title/Wayland)
- **SDL releases**: SDL 3.4.0 (January 2026) added native PNG, atomic KMS/DRM, and Wayland fixes. 3.4.20 (3 November 2026) is reported as the latest stable, with Wayland clipboard fixes. — [SDL 3.4.0 announcement](https://discourse.libsdl.org/t/announcing-sdl-3-4-0/65438); [Phoronix](https://www.phoronix.com/news/SDL-3.4-Released); [GameDev.net 3.4.20](https://gamedev.net/news/6900-sdl-release-3420-released/) (snippets only for version details)
- **SDL scaling on Wayland**: SDL uses `wp_viewporter` for viewport destination and emulated fullscreen modes, and `wp_fractional_scale_v1` (included header). It also uses `wp_color_manager_v1` for output color info. — [SDL_waylandvideo.c](https://github.com/libsdl-org/SDL/blob/main/src/video/wayland/SDL_waylandvideo.c); [SDL_waylandwindow.c](https://github.com/libsdl-org/SDL/blob/main/src/video/wayland/SDL_waylandwindow.c)

  — [wayland-explorer kwin.json](https://github.com/vially/wayland-explorer/blob/main/src/data/compositors/kwin.json); [mutter.json](https://github.com/vially/wayland-explorer/blob/main/src/data/compositors/mutter.json); [weston.json](https://github.com/vially/wayland-explorer/blob/main/src/data/compositors/weston.json); [hyprland.json](https://github.com/vially/wayland-explorer/blob/main/src/data/compositors/hyprland.json)
- KWin: fifo-v1 "supported since Plasma 6.4" (KDE bug, snippet). Phoronix (September 2026) reports commit-timing merged into KWin for Plasma 6.8. COSMIC has an open RFC PR (2026) implementing both. — [KDE bug 491219](https://bugs.kde.org/show_bug.cgi?id=491219); [Phoronix KWin commit-timing](https://phoronix.com/news/KDE-KWin-Wayland-Commit-Timing); [cosmic-comp PR #2797](https://github.com/pop-os/cosmic-comp/pull/2797) (snippets only)
- The SDL developers' frame-pacing concern: "if the SDL window is obscured, vkQueuePresent will block in FIFO, which games typically do NOT like." mpv uses FIFO only when both fifo and presentation-v2 are available. — [SDL PR #11640](https://github.com/libsdl-org/SDL/pull/11640); [mpv PR #15056](https://github.com/mpv-player/mpv/pull/15056) (snippets)
- **Audio**: the SDL3 audio bootstrap order is `PIPEWIRE_PREFERRED`, then PulseAudio, then PipeWire, then ALSA. The "preferred" PipeWire backend falls back if PipeWire's registry enumeration finds no devices. — [SDL_audio.c](https://github.com/libsdl-org/SDL/blob/main/src/audio/SDL_audio.c); [SDL_pipewire.c](https://github.com/libsdl-org/SDL/blob/main/src/audio/pipewire/SDL_pipewire.c)
- **Precedent stack (CPS-2 Recomp)**: "SDL's GPU API (Metal, Vulkan or Direct3D 12), with SDL's renderer where there is no GPU device". Display options are sharp, whole-pixel or smooth scaling and 4:3, square-pixel or full-screen aspect. "RetroArch shaders (CRT, scanlines, xBRZ and more, or your own preset)". Run-ahead, save states, rollback netplay. Android requires Vulkan. Dependencies: SDL 3 (zlib), Dear ImGui (MIT), Inter font. — [docs/TOOLKIT.md](https://github.com/tmcleroy/cps2recomp/blob/main/docs/TOOLKIT.md); [README](https://github.com/tmcleroy/cps2recomp)
- Cannonball, the older precedent, uses SDL 2 with OpenGL, OpenGL ES or plain SDL2 rendering. — [cannonball README](https://github.com/djyt/cannonball)

### Inferences
- **Recommended lowest-risk stack** (my synthesis):
  - **SDL 3.4.x.** Native Wayland when fifo-v1 is present, otherwise XWayland, which is transparent to the port.
  - **Rendering**: SDL_GPU (Vulkan) for a 384×224 framebuffer and slang/RetroArch-format CRT shaders, with SDL_Renderer as the fallback.
  - **Audio**: SDL audio streams over PipeWire.
  - **Input**: SDL gamepad API, which covers 3 controllers and hot-plug, plus keyboard. Raw evdev is unnecessary.
  - SDL2 is in maintenance and lacks SDL3's Wayland work. GLFW has no audio or gamepad mapping layer of SDL's breadth (not researched in depth). Raw libwayland/wlroots means re-implementing fractional scale, viewporter, xdg-decoration and FIFO handling that SDL already ships. None of the three lowers risk.
- **59.637 Hz on 60 Hz panels.** Running the emulated or recompiled frame at 59.637 Hz under FIFO vsync at 60 Hz duplicates one frame about every 2.75 s (inference: the 0.363 Hz difference). Options:
  - Use VRR (fullscreen, or compositor-supported) and pace the game to 59.637 Hz.
  - Lock the game to the display (60 Hz, 0.6% fast, the RetroArch-style approach) and resample audio dynamically.
  - Present with tearing-control on KWin, Weston or Hyprland. Mutter lacks it per the table.
  Commit-timing-v1 (Mutter, Weston, Hyprland; KWin from 6.8) is what allows a client to target presentation times exactly without busy-waiting.
- **Integer scaling.** 224 lines × 4 = 896 fits a 1080p panel and × 6 = 1344 fits 1440p. Fractional desktop scaling should be bypassed by rendering at buffer-pixel resolution, which SDL does with `SDL_WINDOW_HIGH_PIXEL_DENSITY` plus viewporter and fractional-scale.

### Gaps
- No primary SDL wiki page on VRR or presentation-timing APIs was fetched. Whether SDL 3.4 exposes `wp_presentation` feedback to applications is unverified; the fetched window code does not reference it.
- GLFW's 2026 Wayland status was not researched.
- Weston's lack of fractional-scale and Mutter's lack of tearing-control come from the wayland-explorer snapshot (September 2026) and may lag the latest releases.

## 4. Legal and licensing situation (rights holders, re-release history, precedent for disassemblies and decompilations, Capcom's DMCA history, best practice)

### Takeaway
AvP's only official re-release since 1994 is the licensed 2019 Capcom Home Arcade, which emulated the original ROMs with FB Alpha. It was absent from the Capcom Beat 'Em Up Bundle (2018) and both Capcom Arcade Stadium collections (2021, 2022). The press attributes this to licensing, but no source confirms the reason. Capcom's visible GitHub DMCA activity is small: two notices, neither against a disassembly or a decompilation. Industry precedent is mixed. Decomp and recomp repositories without assets mostly stay up. Nintendo targets distributed binaries and assets. Take-Two sued the re3/reVC authors and settled in 2023 on undisclosed terms. The common practice is "no ROM data, no keys, generate locally". CPS-2 Recomp itself documents that its *release binaries contain translated game code*, a risk its maintainer explicitly accepted.

**What precedent projects do in practice**
- CPS-2 Recomp's repo rules: "Never add anything from a game. - **CPS-2 Recomp's release binaries do contain game code.** "Each game's program does hold that game's 68000 and Z80 programs translated to C++ and compiled… That is a form of the games' code, and giving it out is a risk the maintainer has accepted (2026-10-12)." ### Inferences
- **Disassembly with original bytes.** A byte-identical, reassemblable disassembly reproduces every instruction of the program, so on its face it is a copy of the copyrighted code in another notation. Embedding original bytes as `.byte`/`dc.w` data makes that explicit. This is my reading of the precedents, not legal advice. Sega v. Accolade covered *intermediate* copying for interoperability, not publication. That is why the generate-locally pattern exists (ffight-disasm; CPS-2 Recomp's "nothing generated from a game" rule).
- The publishable part is tooling, labels, comments and hand-written reimplementations or rewrites. Generated disassembly, translated C, extracted assets and keys should stay out of public repositories and release artifacts if one follows the more cautious precedents. CPS-2 Recomp's binary releases go beyond that, and the maintainer has documented the decision.
- For AvP specifically there are two rights layers. Capcom owns the code; the Alien and Predator IP sits with Fox, now 20th Century Studios under Disney. The second layer adds a rights holder with a separate enforcement history. That AvP was left out of every Capcom collection except the 2019 licensed Home Arcade suggests rights friction, but this is unconfirmed.
- **Reported takedown patterns.** Nintendo and Take-Two targeted distributed playable builds and assets (SM64 executables) or sued over a project with high visibility (re3). Asset-free tool repositories have generally remained up. A native AvP port's risk profile depends mostly on whether it ships binaries containing translated code, and on its visibility.

### Gaps
- The re3 timeline (GitHub DMCA in February 2021, counter-notice and restoration, lawsuit filed September 2021) is my background knowledge. Only the April 2023 dismissal was confirmed via snippets.
- Disney and 20th Century Studios ownership of the Alien and Predator IP, and Capcom's original 1994 license terms, were not verified with a source in this session.
- Capcom's 2013 statement that AvP was the "most requested" HD port is from a Limited Run Games blog snippet. Not verified; the page was blocked.

## 5. Emulation baseline (MAME/FBNeo on Linux/Wayland) and what a native port adds

### Takeaway
AvP is fully supported in MAME and FBNeo. MAME flags all its sets only `MACHINE_SUPPORTS_SAVE`, with no imperfect-emulation flags, and FBNeo's libretro core supports run-ahead and preemptive frames (about 1 frame of benefit reported for AvP). Both run on Linux through SDL. For a player who only wants the game, emulation is already sufficient. The value of a native port lies in features (three-player conveniences, modes, rollback netplay, mods, widescreen) and in a moddable codebase. CPS-2 Recomp already delivers most of these for AvP, though not widescreen.

### Cited Findings
- MAME: `avsp` (Europe 940520), `avspu`, `avspj`, `avspa` and `avsph` are all declared with `MACHINE_SUPPORTS_SAVE` and no `MACHINE_IMPERFECT_*` or `NOT_WORKING` flags. A bootleg "Phoenix Edition" `avspd` also exists. The driver's known-problems list names Giga Wing and Progear timing issues (the 11.8 MHz approximation), not AvP. — [MAME cps2.cpp](https://github.com/mamedev/mame/blob/master/src/mame/capcom/cps2.cpp)
- RetroArch run-ahead: one tester reported "Aliens vs predator = 1 Frame of run-ahead benefit on FBA". A libretro thread says FBNeo widely supports preemptive frames because it has deterministic savestates. Another thread measured MAME at 1-2 frames more lag than FBNeo in several CPS-era titles. All forum-anecdotal. — [RetroPie forum](https://retropie.org.uk/forum/post/144854); [libretro forum: preemptive frames](https://forums.libretro.com/t/which-arcade-cores-support-preemptive-frames/42131); [libretro forum: FBNeo vs MAME](https://forums.libretro.com/t/finalburn-neo-vs-mame-on-retroarch-windows-10/24465?page=2) (snippets only)
- What CPS-2 Recomp's AvP port adds over emulation:
  - Three players with independent controller mapping, and a Board-page "Players" setting.
  - "Start at round", score attack, an attract-mode looper, and a stage viewer and model viewer.
  - Custom soundtrack, rapid fire, cheats (infinite health, lives, time), operator settings in a menu, "Straight to the title".
  - Run-ahead ("takes a frame or two of input lag away"), save states, speed control and frame advance.
  — [games/avsp/README.md](https://github.com/tmcleroy/cps2recomp/blob/main/games/avsp/README.md)
- The toolkit's rollback netplay is designed so "Every game plays online… with nothing of its own to add". The AvP page does not advertise online play, and the toolkit's checks cover two players. — [docs/TOOLKIT.md](https://github.com/tmcleroy/cps2recomp/blob/main/docs/TOOLKIT.md); [docs/VERIFYING.md](https://github.com/tmcleroy/cps2recomp/blob/main/docs/VERIFYING.md)
- Widescreen in CPS-2 Recomp exists for 16 fighting games but not AvP ("Without widescreen, as before (sfa2, msh, dstlk, avsp, gigawing)"). Cannonball shows that widescreen and higher frame rates are achievable with a full manual rewrite. — [docs/NATIVE_VIDEO.md](https://github.com/tmcleroy/cps2recomp/blob/main/docs/NATIVE_VIDEO.md); [cannonball README](https://github.com/djyt/cannonball)
- Accuracy note: with `arcade_timing` off, which is CPS-2 Recomp's default, the 68000 does about 1.35× the board's work per frame, so slowdown differs from the arcade. MAME approximates the waits with a 0.7375 clock scale. Neither is proven cycle-exact for AvP, since the CPS-2 Recomp comparison covered SFA2 only. — [docs/TIMING.md](https://github.com/tmcleroy/cps2recomp/blob/main/docs/TIMING.md); [MAME cps2.cpp](https://github.com/mamedev/mame/blob/master/src/mame/capcom/cps2.cpp)

### Inferences
- **Is a new native port worth it?** Measured against emulation alone, the gain is moderate: features and moddability, not playability. Measured against CPS-2 Recomp, a new port is justified mainly if it targets something CPS-2 Recomp lacks:
  - widescreen for a beat-'em-up (camera and scene limits are already mapped in CPS-2 Recomp's PROGRESS.md);
  - three-player online play;
  - a fully readable C reimplementation in the Cannonball style;
  - a stricter legal posture (no distributed translated binaries).
  Another option is contributing to CPS-2 Recomp rather than starting over (GPL-3.0-only).
- The byte-identical disassembly is most valuable as documentation feeding a Cannonball-style or "readable rewrite" effort, for example naming the routines at the addresses CPS-2 Recomp lists (camera 0AF858/0B0680, object pool FF9280, player records FF8380).

### Gaps
- No objective latency measurements (input-to-photon) for AvP on MAME, FBNeo or CPS-2 Recomp under Wayland were found.
- FBNeo's AvP compatibility status was not checked against its source.
- Whether CPS-2 Recomp's online play works for AvP's three players in practice is not documented.
